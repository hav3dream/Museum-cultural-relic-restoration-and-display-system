## 1. 项目概述

### 1.1 项目简要说明

本项目旨在开发一套基于 AI 的博物馆文物修复与展示系统，将多种深度学习修复算法（古画修复、壁画修复、语义分割修复、碑刻修复、轮廓提取、融合修复、超分辨率等）与 AI 创作工具（书法生成、书画融合、文本上色、多视角生成、水墨生成等）集成为 B/S 架构的在线平台，并提供在线画廊与数字人吟诗等数字化展示功能。

### 1.2 项目生命周期与阶段划分

采用**预测型（瀑布）生命周期**，原因：需求相对明确、交付物固定、团队规模小、课程周期限定。共划分为 6 个阶段：

| 阶段 | 时间 | 阶段出口（关口） |
|------|------|----------------|
| 启动 | 11-09 ～ 11-13 | 章程批准（M1） |
| 规划 | 11-16 ～ 11-20 | 三大基准批准（M2） |
| 需求分析 | 11-23 ～ 12-01 | 需求基线（M3） |
| 系统设计 | 12-02 ～ 12-10 | 设计评审通过（M4） |
| 实施与测试 | 12-11 ～ 01-08 | 测试通过（M5/M6） |
| 部署收尾 | 01-11 ～ 01-15 | 验收通过、项目关闭（M7/M8） |

### 1.3 参照的标准与文件

- PMBOK 指南（第 6 版）过程框架；
- GB/T 8567《计算机软件文档编制规范》；
- 本仓库 `docs/` 目录下的既有技术文档（API 文档、AI 模型说明）。

## 2. 范围管理计划

- **范围定义**：以《项目范围说明书》（含 WBS）为准，需求条目记录于《需求跟踪矩阵》；
- **范围确认**：每个里程碑关口由指导教师对照范围说明书进行阶段验收；
- **范围控制**：任何新增需求走变更控制流程（见第 12 节）；未经批准的需求不进入 WBS；
- **WBS 分解规则**：100% 原则（WBS 包含全部且仅全部工作）、8/80 工作包粒度原则（最低层任务工期 0.5～3 天）、可交付成果导向分解；
- **责任分配**：WBS 每个工作包在《WBS 与进度计划》中指定唯一责任人。

## 3. 需求管理计划

- **需求收集方法**：文献调研、竞品分析、潜在用户访谈、教师要求梳理；
- **需求文档**：需求规格说明书（SRS），需求编号规则 FR-XX（功能）/ NFR-XX（非功能）；
- **需求跟踪**：《需求跟踪矩阵》建立"业务需要 → 需求 → 设计 → 实现 → 测试"双向追溯链，随需求变更同步更新；
- **需求优先级**：MoSCoW 法（Must/Should/Could/Won't），Must 类需求必须在 M7 验收前实现；
- **需求确认**：M3 里程碑召开需求评审会，指导教师与用户代表签字确认。

## 4. 进度管理计划

- **方法论**：关键路径法（CPM）+ 前导图（PDM），活动间以完成-开始（FS）关系为主，少量 SS 关系；
- **进度工具**：Microsoft Project 制定 WBS、工期、紧前关系并生成甘特图；
- **基准工期**：48 个工作日（2026-11-09 ～ 2027-01-15），每周 5 个工作日，节假日按校历（2027-01-01 元旦放假）；
- **进度基准**：M2 批准后的《WBS 与进度计划》表（含各活动工期与紧前关系）；
- **监控节奏**：每周五汇总实际进度，与基准对比，计算进度偏差（SV）与进度绩效指数（SPI），写入周进度汇报；
- **缓冲策略**：编码阶段（第 6-8 周）预留每日 10% 的机动时间；关键路径上不安排并行学习任务；
- **进度压缩预案**：若 SPI < 0.9，优先采用"快速跟进"（并行任务）而非"赶工"（加班），保护课程学习质量。

## 5. 成本管理计划

- **成本估算方法**：自下而上估算。人力成本按"人天 × 500 元"虚拟核算，GPU 算力按市场租赁价估算，云服务按询价估算；
- **成本基准**：总预算 10.0 万元，按阶段分配：规划与需求 15%、设计 15%、实施 45%、测试 15%、部署收尾 10%；
- **控制阈值**：单阶段成本偏差 ≤ ±5%；累计偏差 > ±5% 时提交变更请求；
- **计量单位**：人民币元，报告粒度到工作包。

## 6. 质量管理计划

### 6.1 质量方针与标准

- 满足《需求规格说明书》中全部 Must 级需求；
- 遵循项目既有工程规范：TypeScript 严格模式（禁用 any）、Prettier 统一格式、每次提交必须通过类型检查（`npm run check`）；
- 数据库结构变更必须通过迁移脚本（migration）管理。

### 6.2 质量度量指标

| 度量项 | 目标值 |
|--------|--------|
| 验收测试用例通过率 | 100%（Must 需求）/ ≥95%（Should 需求） |
| 严重缺陷（一级/二级） | 验收前清零 |
| TypeScript 编译错误 | 0 |
| 核心接口响应时间 | 管理类接口 ≤ 500ms；AI 修复 ≤ 60s（不含排队） |
| 前端 Lighthouse 性能分 | ≥ 75 |

### 6.3 质量保证与控制活动

- **保证（QA）**：每周代码审查（Code Review）一次；里程碑关口文档评审；
- **控制（QC）**：功能测试、兼容性测试（Chrome/Edge/Firefox）、修复效果抽样评审、回归测试；缺陷记录于缺陷跟踪表，按严重/一般/轻微分级。

## 9. 风险管理计划

- **风险管理流程**：识别 → 定性分析（概率×影响矩阵）→ 定量分析（对高风险）→ 规划应对 → 监控；
- **风险登记册**：随项目周报滚动更新；章程所列 R1～R5 作为初始风险条目；
- **应对策略约定**：威胁采用规避/转移/减轻/接受；每个高等级风险须指定责任人并制定应急预案（如 R1 的"预生成演示结果"）；
- **审查频率**：每周例会固定 10 分钟风险审查。

## 12. 变更管理计划

- **变更控制委员会（CCB）**：指导教师（主席）+ 项目经理；一般变更由项目经理审批，基准级变更由 CCB 审批；
- **变更流程**：提出书面变更申请 → 影响分析（范围/进度/成本/质量四维）→ CCB 决策 → 更新基准与相关文档 → 通知全体相关方；
- **配置管理**：代码以 Git 管理（新仓库 `Museum-cultural-relic-restoration-and-display-system.g`），主分支 `master`，功能完成后合并；文档与代码同仓库版本化；每次里程碑打 tag（M1～M8）；
- **基线管理**：范围/进度/成本三大基准一经批准即冻结，修改必须走变更流程。

## 13. 绩效测量与监控

- **每周测量**：实际完成工作包 vs 基准，计算 SV/SPI、CV/CPI；输出至周进度汇报；
- **里程碑审查**：对照验收标准逐项检查，形成阶段评审记录；
- **预警机制**：SPI < 0.9 或关键路径任务延后 ≥ 2 天时，启动纠偏（快速跟进/范围调整申请）。

## 14. 项目收尾安排

- 产品验收通过后完成：项目总结报告、经验教训登记册、全部文档归档至 `docs/`、代码仓库打最终 tag 并归档；
- 组织 1 次复盘会议，输出改进建议。
